# 为什么使用确定性接触凭证

机器人装配失败常横跨规划、控制、接触感知和材料管理。只保存一个“成功/失败”分数，无法回答失败发生在哪个阶段、当时是否越过安全包络，以及仿真结论能否被实机证据支持。

## 问题

仿真器和机器人栈使用不同消息类型、时钟和存储格式。团队若直接围绕某个模拟器编写评测，迁移到实机时通常还要重写判断逻辑。评测脚本若读取任意插件、运行回放命令或覆盖旧结果，还会把验证器变成新的安全风险。

时间戳也会破坏复核。若收据自动加入生成时间，即使输入完全相同，CI 产生的文件也不同，团队无法用哈希确认两次判断相同。

## 方法

ContactReceipt 把控制栈和验收层分开：

```text
 Gazebo / Isaac Sim / ROS 2 / MCAP / 实机日志
                      |
               团队自有导出器
                      |
          +-----------+-----------+
          |           |           |
       trace.json  policy.json  evidence.json
          |           |           |
          +----- 严格解析器 -------+
                      |
        阶段机 + 包络 + 证据清单审计
                      |
       内容寻址、可解释、确定性收据
```

中立轨迹只保留验收事实，不保留可执行控制命令。策略把阶段依赖、允许转移、必需事件和力/力矩限制放在数据里。证据清单只保存受限元数据和摘要。审计器因此不需要网络、机器人 SDK、模拟器或反序列化插件。

## 为什么失败收据使用列表前缀

序号本身可能正是错误来源。若用 `seq <= 首次失败序号` 选择回放范围，一个错误的超大序号会意外包含后续事件。ContactReceipt 改用违规路径中的真实列表位置截取前缀，再把原始 `event_seq` 作为诊断信息保留。这样即使序号断裂，最小失败前缀仍稳定。

前缀只保存哈希和终点，不复制原始事件。评审者拿到授权轨迹后可重新计算；公开收据则不会泄露完整动作或传感器流。

## 为什么没有生成时间

收据中的所有字段都由三份输入和固定算法版本导出。工具不会读取系统时间，集合在输出前排序，JSON 键采用固定顺序编码，数字拒绝 NaN 和无穷。因此相同语义输入会得到相同字节、相同输入指纹和相同 `receipt_id`。

若答辩材料需要签发时间，应由外部签名或提交系统记录，并与收据分开。这样时间元数据不会改变技术判断。

## 为什么不直接解析 bag 或 MCAP

直接解析方便，但会引入 ROS 发行版、消息定义、存储插件和反序列化信任边界。中立 JSON 让每支队伍明确自己的 topic 映射和单位换算，也让同一审计器覆盖多个模拟器。

代价是团队必须维护一个小型导出器。`source_artifact_sha256` 将导出结果与原始记录关联，但本工具不会证明导出器正确；团队仍需用已知样例、消息计数和人工抽查验证映射。

## 为什么证据只做清单

自动打开 `source_uri` 可能触发网络访问、读取隐私文件，或把验证结果绑定到短暂的挂载路径。ContactReceipt 只判断证据元数据是否满足策略，并把整个清单纳入输入指纹。

代价是内容哈希的真实性由证据生产流程负责。更高保证可在外层增加签名、透明日志或受控工件库，而不改变本工具的离线核心。

## 安全包络的边界

包络检查是事后证据验证，不是实时安全控制。它不能阻止机械臂，也不知道工件材料、传感器误差或官方设备限制。阈值必须由合格人员和官方规则决定；真实系统仍需要速度限制、碰撞检测、急停、隔离区和现场监督。

## 取舍与未采用方案

- 选择严格拒绝未知字段，而不是静默忽略，代价是 schema 演进必须显式升级；收益是拼写错误不会悄悄绕过检查。
- 选择独占输出而不是覆盖，代价是重跑要换文件名；收益是原始收据不会被意外替换。
- 选择确定性规则而不是学习型评分器，代价是不能自动推断异常；收益是每个判定都能复现和解释。
- 选择模拟器中立层而不是官方赛题集成，代价是当前原型不能证明赛事表现；收益是赛前可以合法开发通用验收基础，而不伪造官方兼容性。
